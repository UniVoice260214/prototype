# UniVoice 실강의 지연 실측 — 스테이징 (2026-09-26)

AWS 스테이징 서버에서 실제 교수 화면으로 강의를 진행하며 세 번 측정했다.
합성 음성을 반복해 넣은 `latency-results.md`(2026-08-12, 프로브)와 달리 **실제 마이크
발화 · LiveKit · RAG 켜짐 · 4개 언어** 조건이다. 회차마다 한 가지 묶음씩 개선을 켰다.

## 측정 조건

| 항목 | 값 |
|------|-----|
| 환경 | AWS EC2 스테이징 (`docker-compose.staging.yml`), 워커 `LATENCY_LOG_PATH` 계측 |
| 입력 | 교수 화면 마이크로 실제 강의 2~5분 / 회차 (회차마다 발화 내용·양이 다름) |
| STT | Azure Speech `ko-KR` |
| 번역 | OpenAI `gpt-5.4-mini`, 스트리밍, 대상 로케일 `zh-CN`, `vi-VN`, `en-US`, `ja-JP` (1회 호출로 4개 언어) |
| TTS | Azure Neural TTS, 스트리밍 합성 + 선합성 |
| RAG | **켜짐** (`RAG_ENABLED=true`, `RAG_TIMEOUT_SEC=0.4`) |
| 세그먼트 | `SEGMENT_IDLE_FLUSH_MS=2000` (서버 설정) |
| 시간 기준 | 워커 내부 `time.monotonic()`. LiveKit 전송 홉과 학생 단말 재생은 포함하지 않는다 |

## 읽는 법

**1 → 2: 음성이 쌓이는 현상이 사라졌다.** 1회차에서 음성이 늦은 원인은 처리 속도가 아니라
재생 대기열이었다. 번역 음성이 원문 발화보다 길어서(한국어 60자 → 영어 약 7.8초),
교수가 이어 말하면 앞 문장 재생이 끝나기를 기다리는 시간(`ttsQueueMs`, `ttsPlayWaitMs`)이
최대 7~8초까지 쌓였다. 2회차부터는 3초 넘게 기다린 음성을 뒤에 새 문장이 있을 때
건너뛰어, 첫 음성 p50 이 4.5초 → 2.9초, 최대가 10.0초 → 6.6초로 줄었다. 대신 음성
문장의 32%(로케일별 en 4 · ja 4 · vi 3 · zh 3)가 "음성 없이 자막만"으로 처리됐다.
한 STT final 에서 네 문장이 연달아 나온 구간(seq 7~9)에 집중됐다.

**2 → 3: 1.2배속이 건너뛰기를 거의 없앴다.** 3회차는 번역문이 더 길었는데(음성 잡 글자 수
중간값 42 → 58자) 재생 시간 중간값은 4.8초 → 4.7초로 오히려 짧았다. 음성이 덜 밀려
건너뛴 잡이 2건(모두 ja-JP)으로 줄었고, 첫 음성 p50 도 2.45초로 가장 좋았다.
첫 자막은 p50 1.56초, 최대 1.9초로 세 회차 중 가장 빨랐고 번역 슬롯 대기·순서 대기가
한 번도 없었다.

**2회차 자막이 느렸던 이유는 STT 다.** 워커 내부 처리는 1·2회차가 같았고(1.69 / 1.72초),
전체 자막 p50 차이(+0.56초)는 STT 확정 p50 차이(+0.51초)로 설명된다. 여기에 한 final 에서
네 세그먼트가 나와 seq 9 가 동시 번역 상한(`TRANSLATE_MAX_CONCURRENCY=3`)에 1.6초 걸렸다.

## 남은 병목

- **긴 문장 바로 뒤 문장.** 3회차에서 첫 음성이 6~7초였던 경우는 모두 긴 문장 직후다
  (seq 3 → 4, seq 7 → 8). seq 7(한국어 87자)의 음성은 로케일별 8.0~10.3초였고, 뒤 문장은
  뒤에 기다리는 문장이 없어 설계대로 건너뛰지 않고 늦게 재생됐다.
- **`SEGMENT_MAX_CHARS` 는 문장부호로 끝난 문장을 자르지 않는다.** seq 7(87자), seq 12(93자)가
  80 설정에도 그대로 나갔다. 이 설정은 구두점 없이 이어지는 버퍼에만 적용된다.
- **일본어가 가장 길다.** 같은 문장에서 ja-JP 음성이 다른 로케일보다 1~2초 길고, 3회차
  건너뛴 2건이 모두 ja-JP 다.
- **RAG 는 절반 정도만 빠르다.** `ragMs` 가 50ms 미만인 세그먼트가 2회차 6/11, 3회차 7/15 였고
  나머지는 대부분 0.26~0.41초(타임아웃 0.4초 부근)였다.

## 한계

- **회차마다 발화 내용과 양이 다르다.** 같은 WAV 를 반복한 프로브 측정이 아니므로 회차 간
  차이에는 말하는 방식의 영향이 섞여 있다. 특히 STT 확정 시간(358 / 872 / 541ms)은 발화에
  따라 크게 흔들려, `STT_SEGMENTATION_SILENCE_MS` 단축의 효과는 이 데이터로 판단할 수 없다.
- **표본이 작다** (자막 5 / 11 / 15건). p95 는 인용하지 말고 경향으로만 볼 것.
- 3회차는 네 가지 설정을 함께 켰다. 음성 개선은 주로 1.2배속, 자막 개선은 발화 차이와
  B·C·절 분리가 섞인 결과다.
- 임시 자막(`caption.partial`)이 학생 화면에 먼저 보이는 효과는 이 계측에 기록되지 않는다.
- **`translateMs` 음수는 계측 버그다.** 한 STT final 의 첫 세그먼트 등에서 번역 종료 시각이
  기록되지 않아 RAG 종료 이전 시각으로 대체된다(`pipeline.py` 의 `t_translate` 폴백).
  동작에는 영향이 없고 이 필드만 틀린다. 위 표는 이 필드를 쓰지 않는다.

## 재현

1. 워커 compose 환경변수에 `LATENCY_LOG_PATH: /tmp/latency.jsonl` 을 넣고 워커를 재시작한다.
2. 교수 화면에서 새 수업을 열고 강의한 뒤 수업을 종료한다.
3. 서버에서 파일을 꺼내 집계한다.

```bash
docker compose --env-file .env.staging -f docker-compose.staging.yml cp ai-worker:/tmp/latency.jsonl ~/latency.jsonl
```

```bash
python ai-worker/tools/latency_report.py --input docs/latency-run-2026-09-26-3-tuned.jsonl
```
