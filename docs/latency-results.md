# UniVoice 실시간 지연 실측 (2026-08-12)

## 측정 조건

| 항목 | 값 |
|------|-----|
| 표본 | 자막 세그먼트 **60건** / 음성 잡 120건 |
| 입력 | `bench_data/synthetic_ai_intro.wav` (18.0초, 16kHz mono) × 12회 연속 |
| STT | Azure Speech `ko-KR`, `koreacentral`, 침묵 대기 800ms |
| 번역 | OpenAI `gpt-5.4-mini`, 대상 로케일 `vi-VN`, `zh-CN` (1회 호출로 2개 언어) |
| TTS | Azure Neural TTS (로케일당 1건 → 세그먼트당 2건) |
| RAG | **off — 미측정** (아래 "RAG 는 왜 없나" 참조) |
| 하네스 | `ai-worker/tools/latency_probe.py`, 벽시계 드리프트 **+8ms** |
| 원본 데이터 | `docs/latency-run-2026-08-12.jsonl` |

- 시간 기준은 `time.monotonic()`, 워커 프로세스 내부 계측.
- "발화 종료"는 STT 오디오 타임라인(`offset + duration`)으로 역산한 시각이다.
- **LiveKit 전송 홉과 학생 단말 렌더링·재생은 포함하지 않는다.** 워커가 발행한 시점까지다.

## 읽는 법

**(RAG off 기준) 지연의 97%가 두 곳에서 나온다** — STT 침묵 대기(890ms, 46%)와
번역 LLM(985ms, 51%). 세그먼트 확정·큐·발행은 합쳐서 1ms 수준으로, 파이프라인
자체는 병목이 아니다. RAG 를 켜면 여기에 세그먼트당 최대 0.4초가 더 붙는다.

STT 890ms 중 800ms 는 설정값(`STT_SEGMENTATION_SILENCE_MS`)이다. 말이 끝났는지
판단하려고 의도적으로 기다리는 시간이며, 줄이면 문장이 잘게 쪼개져 번역 품질이
떨어지는 트레이드오프다.

**큐 대기는 세그먼트 20%에서만 발생한다.** 한 STT final 에 두 문장이 들어오면
(예: "안녕하세요, 인공지능 입문 수업을 시작하겠습니다") 세그먼트 컨슈머가 직렬이라
뒷문장이 앞문장의 번역을 기다린다. 60건 중 정확히 12건(회차마다 1건)이 이 패턴이고,
대기가 없는 48건만 보면 **E2E 자막 p50 은 1,904ms** 다. 컨슈머를 병렬화하면
회수되는 지연이다.

## RAG 는 왜 없나

이번 실행은 `NoOpRagClient` 로 돌았다 — **RAG 호출 자체가 없었다.**
`ai-worker/.env` 에 `RAG_ENABLED` 가 없어 기본 `false` 이고, `rag-service` 도
띄우지 않았다. 따라서 위 표의 RAG 행은 "0ms(빠름)"가 아니라 "미측정"이다.

> 원본 `latency-run-2026-08-12.jsonl` 에는 `ragMs: 0.0` 이 남아 있는데, 이는
> no-op 클라이언트가 즉시 반환한 값이다. 이후 코드에서는 RAG 가 꺼져 있으면
> `ragMs` 를 아예 기록하지 않아 이런 오독이 생기지 않는다.

### 켰을 때 얼마나 붙나

RAG 는 번역 **직전 크리티컬 패스에 동기로** 걸리므로 위 E2E 에 그대로 더해진다.

- 상한은 `RAG_TIMEOUT_SEC` = **0.4초** (fail-open — 초과하면 문맥 없이 번역).
- `rag-experiment` 벤치마크(kure, CPU)는 검색 E2E p95 **119ms** 로 나왔으나,
  같은 보고서의 재측정에서는 p50 312ms / p95 457ms 로 3~4배 차이가 났고
  **원인이 미확정**이다 (`rag-experiment/REPORT.md` 7절).
- 즉 실제로는 **세그먼트당 +0.1 ~ +0.4초** 사이 어딘가이며, 이 값은 아직
  이 파이프라인 안에서 실측된 적이 없다.

발표에서 RAG 오버헤드를 인용하려면 이 구간을 직접 측정해야 한다. 필요한 것은
`rag-experiment/indexes/` 의 FAISS 인덱스 구축(현재 비어 있음)과 `rag-service`
기동이며, 그 뒤 프로브에 `--rag` 를 붙이면 위 표에 RAG 행이 채워진다.

## 재현 / 한계

재현 절차는 `docs/latency-measurement.md`. 요약:

```bash
cd ai-worker
.venv/Scripts/python.exe tools/latency_probe.py \
    --wav bench_data/synthetic_ai_intro.wav --locales vi-VN,zh-CN \
    --major ai --repeat 12 --tail-sec 4 --out latency.jsonl
.venv/Scripts/python.exe tools/latency_report.py --input latency.jsonl
```

- p50 은 독립 실행 2회(20건 / 60건)에서 1,936ms / 1,950ms 로 재현됐다.
  p95 는 번역 LLM 분산 때문에 흔들린다(3,167 ~ 3,810ms).
- 합성 강의 샘플 1개를 반복한 결과다. 실제 강의의 발화 길이·잡음 분포와 다를 수 있다.
- 하네스가 오디오를 실시간·무중단으로 넣지 않으면 STT 확정 구간이 부풀어 오른다.
  프로브가 출력하는 드리프트가 500ms 를 넘으면 그 측정은 버려야 한다.
